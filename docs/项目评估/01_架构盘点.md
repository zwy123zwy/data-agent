# Phase 1: 架构盘点

> 评估日期：2026-05-09
> 项目版本：v0.2.0

## 1. 工作流引擎 — LangGraph 16 节点状态机

### 节点拓扑（三阶段设计）

**第一阶段：前置处理（线性，任意失败 → END）**

```
Intent → KnowledgeRecall → QueryRewrite → SchemaRecall → TableRelation → Feasibility → Planner
```

**第二阶段：循环调度（PlanExecutor 中枢）**

```
PlanExecutor ──→ SQL_GENERATE  → SqlGenerate → SemanticCheck → SqlExecute ──┐
              ├── PYTHON_GENERATE → PythonGenerate → PythonExecute → PythonAnalyze ──┤
              ├── REPORT_GENERATOR → ReportGenerator                                      │
              └── HUMAN_FEEDBACK → HumanFeedback                                      │
                  ▲ (approve/reject 后回到 PlanExecutor 或 Planner)                    │
                  └─────────────────────────────────────────────────────────────────────┘
```

**第三阶段：收尾**

```
ReportGenerator → END (SSE event:complete)
```

### 16 节点完整清单

| # | Python 节点 | Java 对齐 | 核心职责 | 失败策略 |
|---|-----------|----------|---------|---------|
| 1 | `intent_recognition` | IntentRecognitionNode | LLM 识别意图：data_analysis / chitchat / unanswerable | 非 data_analysis → END |
| 2 | `knowledge_recall` | EvidenceRecallNode | RAG 召回 Agent 知识和业务知识，注入后续 prompt | — |
| 3 | `query_rewrite` | QueryEnhanceNode | 多轮上下文注入 + 查询改写 | 空 → END |
| 4 | `schema_recall` | SchemaRecallNode | 按 Agent 激活数据源召回表结构 DDL | 空 → END |
| 5 | `table_relation` | TableRelationNode | LLM 发现表间 JOIN 关系 | 最多 3 次重试，超限 → END |
| 6 | `feasibility` | FeasibilityAssessmentNode | 评估问题与 Schema 的匹配度 | 不可行 → END |
| 7 | `planner` | PlannerNode | 生成多步骤执行计划 (SQL/Python/Report/HF) | — |
| 8 | `plan_executor` | PlanExecutorNode | 校验 Plan 结构 + 按 step 路由 | 修复超限 3 次 → END |
| 9 | `sql_generate` | SqlGenerateNode | LLM 生成 SQL | 最多 10 次重试 |
| 10 | `semantic_consistency` | SemanticConsistencyNode | 校验 SQL 语义（表和字段是否匹配 Schema） | 不通过 → 重新生成 |
| 11 | `sql_execute` | SqlExecuteNode | 在业务库执行 SQL | 失败 → 重新生成 |
| 12 | `python_generate` | PythonGenerateNode | LLM 生成 Python 数据分析代码 | — |
| 13 | `python_execute` | PythonExecuteNode | 执行 Python 代码 (Local/Docker/AISim) | 最多 5 次重试，超限 → 降级到分析 |
| 14 | `python_analyze` | PythonAnalyzeNode | LLM 分析 Python 执行结果 | — |
| 15 | `human_feedback` | HumanFeedbackNode | LangGraph interrupt() 暂停等待人工审批 | 拒绝 3 次 → END |
| 16 | `report_generator` | ReportGeneratorNode | 生成 HTML/Markdown 报告（含 ECharts） | — |

### 重试机制

| 重试点 | 最大次数 | 配置键 |
|--------|---------|--------|
| TableRelation 异常 | 3 | 硬编码 |
| SQL 生成/执行失败 | 10 | `max_sql_retry_count` |
| SQL 语义校验失败 | 受 SQL 次数约束 | — |
| Python 执行失败 | 5 | `code_executor.python_max_tries_count` |
| Plan 校验失败 | 3 | `max_plan_repair_count` |
| HumanFeedback 拒绝 | 3 | 硬编码 MAX_REJECT_COUNT |

## 2. 工具调用链

### SQL 工具链

```
SqlGenerate (LLM 生成 SQL)
  → SemanticConsistency (校验表和字段是否存在于 Schema)
    → SqlExecute (aiomysql 执行，返回结果集 JSON)
```

### Python 工具链

```
PythonGenerate (LLM 生成 pandas/matplotlib 代码)
  → PythonExecute (subprocess 执行，数据通过 JSON 文件注入)
    → PythonAnalyze (LLM 分析执行结果，生成文字结论)
```

### 报告生成

```
ReportGenerator (整合 SQL 结果 + Python 图表 → HTML/Markdown 报告)
  → 支持 ECharts 图表嵌入
  → TextType: HTML / MARK_DOWN
```

### 代码执行器三种模式

| 模式 | 实现状态 | 说明 |
|------|---------|------|
| `local` | ✅ 已实现 | subprocess.run，临时目录隔离，30s 超时 |
| `ai-sim` | ✅ 已实现 | LLM 模拟执行结果（快速原型） |
| `docker` | ❌ 未实现 | 接口已定义，返回 "未实现" |

## 3. 记忆与上下文

### 会话管理

- **Session**: `chat_session` 表，支持 `is_pinned`、`rename`、`delete`
- **Message**: `chat_message` 表，5 种 messageType：`text` / `html` / `result-set` / `html-report` / `markdown-report`
- **标题自动生成**: `SessionTitleService` 通过 `GET /api/agent/{id}/sessions/stream` SSE 推送 `event: title-updated`
- **9 个会话/消息 REST 端点** 完全对齐 Java 前端

### 多轮对话

- `MultiTurnContextManager`: 内存存储，threadId → turns 列表
- 每轮截断到 `max_turn_history=5`，注入 prompt 前缀
- `QueryRewrite` 节点结合历史上下文改写当前查询

### 状态持久化

- **当前**: `MemorySaver`（进程重启丢失）
- **规划**: `SqliteSaver` 或 `PostgresSaver`

## 4. RAG — 检索增强生成

### 架构

```
用户提问 → knowledge_recall_node
  → KnowledgeService.search_knowledge()
    → VectorStore.search() (Chroma + bge-m3 embedding)
    → 返回 top_k 条知识
  → 知识文本注入后续 LLM prompt
```

### 向量存储

| 特性 | 当前实现 |
|------|---------|
| 引擎 | Chroma（本地 PersistentClient） |
| 持久化路径 | `./chroma_data/` |
| Embedding 模型 | bge-m3（通过 Ollama / OpenAI 兼容 API） |
| 相似度算法 | 余弦相似度 (cosine) |
| Agent 隔离 | 每个 Agent 独立 collection: `agent_{id}_knowledge` |
| 混合检索 | RRF 算法已实现 (`HybridSearchService`)，但未集成到主流程（`hybrid_search_enabled=false`） |

### 召回类型

1. **Agent 知识** (`KnowledgeService`): 用户上传的业务知识，存储在 `knowledge` 表 + Chroma
2. **业务知识** (`BusinessKnowledgeService`): 系统级业务知识
3. **Schema 召回** (`SchemaRecallNode`): 从 MySQL 实时读取表结构 DDL

## 5. HumanFeedback — 人在回路

### Interrupt/Resume 流程

```
1. 请求携带 humanFeedback=true
2. PlanExecutor 检测 human_review_enabled=True → 路由到 human_feedback
3. human_feedback_node 调用 LangGraph interrupt({"type": "human_feedback", ...})
4. 图暂停 → streaming controller 捕获 __interrupt__ 事件
5. 发送 SSE event: paused → 前端展示审批组件
6. 用户 approve/reject → 前端重新请求 GET /api/stream/search?threadId=xxx&humanFeedbackContent=xxx
7. 后端构建 Command(resume={"action": "approve/reject"})
8. 图从 interrupt 处恢复 → 继续执行或重新规划
```

### 三种路由

| 动作 | 下一步 | 状态 |
|------|--------|------|
| approve | plan_executor | 继续执行计划 |
| reject (1-2次) | planner | 重新规划 |
| reject (≥3次) | END | 工作流终止 |

## 8. 工程边界

### API 层

- **18 个 REST Controller**，13 组路由注册
- **SSE 协议** 完全对齐 Java `GraphNodeResponse` 格式
- **7 种 TextType**: SQL / JSON / HTML / MARK_DOWN / RESULT_SET / PYTHON / TEXT
- **3 种 SSE event**: `data:` (无前缀) / `event: complete` / `event: error` / `event: paused`

### 数据层

- **16 个 ORM Model**，MySQL + aiomysql 异步驱动
- **8 种数据库适配器**: MySQL / PG / SQLite / Oracle / SQL Server / ClickHouse / 达梦 / Hive
- 连接池 10+20，自动建表 `Base.metadata.create_all`

### 配置层

- Pydantic Settings 结构化配置，`.env` 文件驱动
- 支持 LLM 模型热切换（OpenAI 兼容协议）

### 错误处理

- 统一 `ApiResponse` 中间件
- 全局异常处理器
- 三层错误处理：节点级 → 工作流级 → API 级
